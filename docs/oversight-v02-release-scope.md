# Proposed sm-oversight 0.2 release scope

An independent executor should be able to establish who approved an exact operation, perform it once under the applicable policy, and produce evidence of its outcome. This is proposed work. Baseline 9d5fb4f, nine passing tests on Python 3.12.

## Immediate maintenance release

Publish a 0.1.x advisory explaining the limits of historical records. Reproduce the changed payee, corrupted execution signature, copied issuer vote, invalidated issuer signature after witnessing, zero threshold and repeated grant use. Reject malformed inputs and invalid thresholds, verify the execution signature, and label legacy results accurately. Provide a distinct legacy inspection API. If callers relied on the legacy gate as execution permission, fail closed and require explicit migration. Inventory downstream sm-dissociation-receipt and guard integrations and exercise their actual entry points before rollout. Preserve original evidence bytes.

## Wire contract

1. A signed pending proposal carries a versioned intent. Include principal, agent, executor audience, operation and schema version, target, material arguments, unique request ID and deadline. Use explicit representations for amounts, currency, time and optional fields. Define JCS canonicalization, digest algorithm, byte limits, duplicate-key rejection, supported numeric ranges and unknown critical fields. Use integer minor units in the purchase profile. Each adapter defines the fields that can change the effect and derives them from the final outbound request. Opaque operations without an installed schema fail closed.
2. The immutable decision receipt identifies the signed proposal by ID and digest, intent digest, policy digest, decision, expiry and use limit. The profile requires an explicit grantee and exact category. Cross-check principal, agent, audience and issuance order. A grant alone conveys no quorum. Approval, denial, escalation and change requests are distinct outcomes. An amended intent gets a new proposal.
3. Detached votes sign a typed, versioned statement containing the signed decision digest, policy digest, decision and signer identity. Define deterministic signing bytes with a protocol-specific purpose tag. Transport votes alongside the immutable receipt. Verify receipt issuer and witness signatures separately. Demonstrate that signatures cannot move between roles, receipts, policies or protocol versions. Any authorized coordinator may assemble the bundle under configured issuer policy.
4. Define authenticated, versioned policy snapshots and trusted issuer configuration. Ship owner-only and M-of-N profiles. Validate positive integer thresholds and distinct eligible signers. Map credentials to eligible people and roles through the relying party’s trust configuration. Multiple keys belonging to one enrolled person count once. Include a separation-of-duties fixture. Specify rotation, revocation, decision-time eligibility, executor-time status checks and stale or unavailable evidence. Historical verification returns indeterminate when evidence is missing.

## Runtime contract

Expose separate operations for proposal construction, review, preflight verification, atomic reservation and historical verification. A pure verification result alone never reserves authority. The resource server owns enforcement and the final adapter. Read current time from its clock, validate expiry at reservation, verify proposal and decision signatures, check quorum and policy, recompute intent, validate any required standing delegation and check current decision status. Reject unsupported profiles with stable reason codes. Validate untrusted sizes and nesting before expensive signature work.

Provide a durable reference executor with an atomic unique reservation per approval and executor, including across replicas. Store the request fingerprint and provider idempotency key before submission. Model reserved, submitted, succeeded, definitively failed and outcome unknown. A retry with identical intent returns the recorded result or reconciles the pending one. A different fingerprint fails. Specify crash recovery before and after external submission. A provider without safe idempotency or reconciliation requires manual resolution after an ambiguous submission.

Define one authoritative status and reservation boundary per approval. Serialize withdrawal and reservation. Withdrawal wins if committed first. Once reserved, return the actual state and require an explicit cancellation workflow where supported. Escalation blocks execution until the proper authority resolves it under policy. An offline verifier can inspect signatures and past evidence. A live executor requiring fresh status fails closed during a partition. Record a signed reservation or execution-time decision, followed by a linked signed outcome receipt. Audit expiry and authority as of the decision to execute.

## Personal agent and organizational profiles

Demonstrate a private assistant proposing a specific booking, an owner reviewing it on a separate surface, and an independently configured executor. Render price, currency, itinerary, passenger reference, terms and expiry from the committed intent. Use a real owner-authentication adapter for the reference flow and document key custody, recovery and assurance limitations. The host and agent must be unable to cast the owner's vote using their own credentials. Display approved, submitted, booked, withdrawn and unknown as distinct states. Demonstrate a fare change, owner withdrawal and a duplicate submission. A second fixture exercises two different organizational reviewers.

NANDA Connect may provision the discoverable agent binding. Its listing grant carries no booking authority. sm-dat may authorize routine searches or constrain subsequent actions. Any required DAT and per-action approval must both pass. A private assistant requires no public listing. Keep personal itineraries and review history out of the registry. Store sensitive evidence locally behind access control, with selective disclosure, limited retention and protection against guessing low-entropy private fields from exported digests.

## Evidence, migration and release gates

Publish a language-neutral schema, signing vectors and a versioned evidence bundle. Include what the reviewer was shown, the review trigger, signer role, policy reference, decision, status evidence and actual outcome. Distinguish evidence of presentation from a claim that the person understood it. Publish separate mappings for EU high-risk system intervention, Singapore agentic checkpoints, US voluntary risk management and Brazilian post-decision recourse. Track applicability, source and mapping date. Recourse can reference an original case without placing personal details in portable evidence.

Ship a migration guide, CLI verification example, updated threat model, specification, README, changelog and downstream compatibility matrix. Dispatch only by explicit version. Preserve legacy inspection, never upgrade a legacy vote into exact-action authorization, and require fresh approval for outstanding legacy jobs. Rehearse rollback with queued and in-flight work.

Release acceptance requires all six baseline reproductions to have explicit expected outcomes, signed fixture verification by an independent implementation, negative vectors for swapped fields and identities, expired or unknown authority, duplicate keys and unsupported versions, concurrent reservations and withdrawal races, crash recovery, old-record inspection and cross-package CI against published minimum and candidate ARP. Run the private personal-agent flow and organizational quorum flow through their normal entry points. Publish only after the downstream gate rejects legacy authority for new privileged actions.
